---
name: RevenueCat native identity
description: Account-linking and migration rules for Natively-managed RevenueCat purchases.
---

Use a single, non-guessable, server-issued per-account RevenueCat App User ID across iOS and Android. Preserve the already-issued opaque identity of existing Android purchasers exactly, even if the derivation secret later rotates. Sign in to this identity through the documented Natively bridge **before** presenting a paywall or starting a native purchase.

**Why:** The user explicitly chose a cross-platform opaque ID rather than an exposed or sequential Roster identifier. RevenueCat can fail to merge existing custom IDs and anonymous aliases; silently renaming an established purchaser risks orphaning paid access. Secret-derived identities can also change when a server secret rotates unless each assigned identity is retained.

**How to apply:** Treat anonymous/other legacy customers as a separate ownership-checked migration, not an automatic alias. For the new native flow, use RevenueCat's verified server-side entitlements as the paid-access authority, not Natively callback success or an additional raw store-receipt check. Preserve independent Stripe and legacy purchase access.

On 2026-09-30, an App Store-installed Natively iPad build returned an anonymous customer ID from both `login` and repeated `customerId` reads despite a successful eligibility response. The JavaScript call matches Natively's documented method signature. The root cause in that native build is unconfirmed; do not treat its callback as proof of identity or permit purchases while read-back remains anonymous. Natively documents that changes to its In-App Purchases configuration require a rebuilt native app. The user declined TestFlight testing, so real Apple sandbox purchase and restore verification remains blocked unless another confirmed sandbox-capable native build is available.

The user confirmed that purchases from the existing in-app Subscriptions screen reach RevenueCat and that the installed iOS release was rebuilt after the purchase settings were saved. Do not repeat generic setup/rebuild questions for this failure. Working purchases establish that the purchase bridge operates, but **do not establish that the first-sign-in custom-ID login succeeded**; isolate the onboarding timing/identity response separately. **Why:** The working Subscriptions screen uses the same account-link helper but is reached later in the session, while the first-sign-in flow received anonymous login and read-back IDs.

RevenueCat's [identity documentation](https://www.revenuecat.com/docs/customers/identifying-customers) says an anonymous identity can be aliased to a custom one while `original_app_user_id` remains anonymous; the current `app_user_id` becomes the custom ID. An anonymous value from a wrapper's `customerId()` might indicate either a failed login **or** a wrapper mistakenly exposing the original ID. This is a hypothesis for Natively, not a verified bug. **How to apply:** Ask the native bridge provider whether its login callback waits for `logIn` and whether `customerId` maps to the SDK's current `appUserID` or to `CustomerInfo.originalAppUserId`. Do not weaken exact-ID verification based on alias theory alone.

The app's eligibility check reads RevenueCat's v1 subscriber endpoint **before** native login. RevenueCat calls it "get or create", so the custom ID existing in RevenueCat is not evidence that native login succeeded. A later original anonymous ID under that custom account is consistent with aliasing, but does not prove it belongs to the current device. **How to apply:** Compare only a SHA-256 hash of the current device's high-entropy anonymous ID to the server-fetched original ID for the authenticated allowlisted tester. A match helps diagnose bridge semantics, never authorizes billing or replaces the exact native current-ID guard.

The on-device hash comparison **matched** the anonymous ID returned by Natively's `login` and repeated `customerId` calls to RevenueCat's original anonymous ID under the signed-in custom account. **Why:** This confirms that the original ID belongs to the affected device rather than merely appearing under an unrelated customer, but still cannot distinguish whether the wrapper returns `originalAppUserId` or the native SDK remains on the anonymous current ID. **How to apply:** Require an authoritative current `appUserID` read-back or a native bridge fix before changing the exact-ID purchase guard; don't infer purchase identity from the RevenueCat subscriber record or original-ID match.
