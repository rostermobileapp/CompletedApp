---
name: Scrimmage wall-clock timestamps
description: Why scrimmage date/time values must remain league-local strings from database write through client display.
---

Scrimmage times and payment deadlines are wall-clock values in the league timezone. Never pass a JavaScript `Date` to a scrimmage `date_time` or date-only payment deadline write; use Drizzle string mode and preserve the league-local components. Client scrimmage views must likewise parse stored components as a wall-clock value rather than letting the browser reinterpret a trailing `Z`. Monthly recurrence must calculate every occurrence from the original local day-of-month anchor; clamp only the individual short month, then resume the anchor afterward.

**Why:** These columns are PostgreSQL `timestamp without time zone`. A recurring 9:00 PM Eastern time converted to a `Date` was serialized as 1:00 AM UTC, so different users saw the wrong clock time; Drizzle's default timestamp mode also calls `toISOString()`, which crashes when a date-only form string is passed. Repeatedly adding one month to a clamped February date permanently moved a series anchored on the 29th, 30th, or 31st to an earlier day.

**How to apply:** Use timezone-aware `Date` objects only for instant comparisons and recurrence arithmetic. Compare recurrence end boundaries as league-local `yyyy-MM-dd` keys so the selected final day is inclusive, and use the same local date key when checking whether a generated child already exists; UTC/server-local day bounds can miss the row and create duplicates. A date-only value returned by Drizzle as a `Date` must recover its persisted wall-clock day from its UTC components rather than shifting it through the league timezone. For monthly series, retain the original league-local date/time components and derive each offset independently. At storage and display boundaries, preserve the original league-local date and clock components, and declare date-only timestamp columns with `{ mode: 'string' }`.
