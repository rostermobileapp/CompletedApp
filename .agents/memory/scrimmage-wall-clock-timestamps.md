---
name: Scrimmage wall-clock timestamps
description: Why scrimmage wall-clock values use an immutable creator timezone from creation through display and lifecycle checks.
---

Scrimmage times are wall-clock values in an immutable timezone captured from the creator's profile when the scrimmage is created. Do not derive an existing scrimmage's timezone from the league or the creator's current profile. Never pass a JavaScript `Date` to a scrimmage `date_time` or date-only payment deadline write; use Drizzle string mode and preserve the creator-local components. Client scrimmage views must likewise parse stored components as a wall-clock value rather than letting the browser reinterpret a trailing `Z`. Monthly recurrence must calculate every occurrence from the original local day-of-month anchor; clamp only the individual short month, then resume the anchor afterward.

**Why:** These columns are PostgreSQL `timestamp without time zone`. A recurring 9:00 PM Eastern time converted to a `Date` was serialized as 1:00 AM UTC, so different users saw the wrong clock time; Drizzle's default timestamp mode also calls `toISOString()`, which crashes when a date-only form string is passed. Repeatedly adding one month to a clamped February date permanently moved a series anchored on the 29th, 30th, or 31st to an earlier day. Legacy monthly children may also retain dates produced by the former fixed-30-day formula even after the generator is corrected.

**How to apply:** At creation, copy the creator's profile timezone onto the scrimmage and copy it to every recurring child; treat it as immutable afterward. Use timezone-aware `Date` objects only for instant comparisons and recurrence arithmetic. Every scrimmage lifecycle guard—join, approval, backup response/cutoff, payment, finalization, and withdrawal windows—must first interpret `date_time` in the persisted scrimmage timezone; never call `new Date(date_time)` directly for these checks. Use that timezone for invites, reminders, emails, and calendar-date visibility too. Compare recurrence end boundaries as creator-local `yyyy-MM-dd` keys so the selected final day is inclusive, and use the same local date key when checking whether a generated child already exists. For monthly series, retain the original local date/time components and derive each offset independently. When repairing legacy children, move only rows that exactly match the old calendar-date-plus-30-days formula; a different date may be an intentional organizer reschedule.
