# 2. BEHAVIOR

- Once per day, every user gets the same hockey trivia question.
- Each question is multiple choice with exactly 4 options.
- Each user can answer once per day. Store the answer and whether it was correct.
- "Day" is defined in America/New_York time, not UTC or device time.

# 3. POPUP MODAL (iOS and Android)

- On app open, if the user hasn't answered today's question, show a popup modal. This applies to free and paid users alike.
- Modal contents: category label, question text, exactly 4 tappable answer buttons, and a "Not now" / close button. For paid users, also show the category's patch icon.
- Tapping an option submits immediately and locks the answer. The modal then shows correct/incorrect, highlights the right answer, shows the explanation, and shows the user's current streak.
- Post-answer feedback for PAID users:
  - If correct: show "+1 toward [Category] patch" with an animated progress bar toward the next tier threshold.
  - If the answer unlocked a new tier: show a celebratory unlock moment with the patch art and Tier number, using the same celebration/notification pattern the existing patch system uses. Optionally send a OneSignal push if that's how other patch unlocks notify.
  - If incorrect: show the correct answer and explanation, and the patch's current progress unchanged.
  - Include a "View in Trophy Case" button that opens the relevant patch, plus a "Done" button.
- Post-answer feedback for FREE users:
  - Show correct/incorrect, the explanation, and the streak, with a "Done" button.
  - If correct, show a subtle, non-blocking teaser such as "You've got X correct in [Category]. Upgrade to unlock trivia patches." with a button that opens our existing upgrade/paywall flow. Keep it to one compact line and button. Do not interrupt the answer flow, and never show it before the user has answered.
  - Free users never see tier unlock celebrations and never receive patch-unlock pushes. Their counts still accumulate silently.
- If dismissed with "Not now", don't show again until the next app launch that day. Once answered, never show again that day.
- Never show the modal in the middle of an active task (editing a lineup, mid-game scoring, etc.). Show it only on app launch or when returning to the home screen.
- Accessibility: large tap targets, screen reader labels, light and dark mode support.

# 4. DATA MODEL

Table `daily_trivia`:
- id, date (unique, YYYY-MM-DD, Eastern), category, question, choices (JSON array of exactly 4), correct_index (0-3), explanation, difficulty (easy/medium/hard), verification_status (verified / fallback), verification_notes, created_at

Table `trivia_answers`:
- id, user_id, trivia_date, category, chosen_index (0-3), is_correct, progress_awarded (0 or 1), answered_at
- Unique constraint on (user_id, trivia_date)

Table `trivia_fallback`:
- Same fields as daily_trivia minus date, plus used_on. Seed with 30 well-known, easy-to-verify hockey questions (4 choices each), spread across all 9 categories, each with a category and difficulty. Mark used_on when used so none repeat.

Table `trivia_category_patches` (config):
- category, patch_id. Editable without a deploy.

Table or config `trivia_tiers` (one shared tier table, not hardcoded in logic):
- tier number, correct_answers_required (see section 7)

Per-user, per-category stats (answered, correct, current tier, unlock date per tier). Track these for all users, free and paid. Reuse existing patch tables if they already track this.

# 5. DAILY GENERATION JOB

Create a Scheduled Deployment (cron) that runs daily at 12:00 PM (noon) America/New_York. Use the America/New_York time zone setting, not a fixed UTC offset, so it stays at noon local time through daylight saving changes.

The job generates TOMORROW's question (target_date = tomorrow in Eastern time), so it is always ready before midnight. The trivia "day" still rolls over at midnight Eastern for users.

1. Skip if a row already exists for target_date.
2. Pick the category for target_date using a weekday rotation of these 9 categories: NHL History, Stanley Cup, Players & Legends, Records & Stats, Teams & Franchises, Hockey Culture, Movies & Media, Nicknames & Slang, Arenas & Fans.
   - Also support occasional special FORMATS: "This Day in Hockey History" (tied to target_date's calendar date), "Name That Player" (3 clues), "Who Am I?" (career path), "Stat Line Mystery."
   - Special formats are a presentation style, not a category. Every question must still carry one of the 9 categories above, and that category determines which patch it counts toward. The generator prompt and schema validation must require this.
3. Load the last 60 questions and pass them to Claude so it avoids repeats and near-duplicates.
4. GENERATE: Call the Claude API (model `claude-sonnet-5-5`) asking for ONE multiple-choice question with exactly 4 options as strict JSON: {category, question, choices[4], correct_index, explanation, difficulty, source_basis}. Rules in the prompt:
   - Only use facts you are highly confident are correct and widely documented.
   - Avoid obscure stats, disputed records, or anything that changes over time (current rosters, standings, active-player career totals).
   - Exactly one unambiguously correct answer; the 3 distractors must be plausible but clearly wrong.
   - Question under 200 characters, each option under 40 characters (must fit a phone modal), explanation 1 to 2 sentences.
5. VERIFY (separate API call, fresh context, does not see the generator's reasoning): Give the verifier the question and the 4 choices WITHOUT telling it which is keyed correct. Ask it to independently pick the answer, then compare. Also ask it to check: (a) is the keyed answer actually correct, (b) is any other choice also arguably correct, (c) is the question time-sensitive or ambiguous, and (d) its confidence (high/medium/low). Return strict JSON.
6. Publish only if the verifier's independent answer matches correct_index, no other choice is arguably correct, and confidence is "high". Otherwise regenerate (max 3 attempts total), passing the failure reason into the next attempt.
7. If all attempts fail or the API errors, use an unused row from trivia_fallback and set verification_status = "fallback". The day must never be empty.
8. Log every attempt (question, verdict, notes) so I can review failures, and send me an email or log alert whenever a fallback is used.

Safety net: if GET /trivia/today ever finds no row for today (job failed, outage), it must immediately pull an unused fallback question, save it for today with verification_status = "fallback", and alert me.

# 6. API ENDPOINTS (all require auth)

Trivia endpoints (open to all authenticated users):
- GET /trivia/today: returns today's question, the 4 choices, category, difficulty, and whether this user has already answered. For paid users, also include the category's patch info. NEVER include correct_index or explanation until the user has answered.
- POST /trivia/answer: body {chosen_index} (integer 0-3). Rejects if already answered today. Must be idempotent. Returns: is_correct, correct_index, explanation, updated streak, category, and the user's new correct count for that category. For paid users, additionally return the next tier threshold and whether this answer unlocked a new tier (with the tier number). For free users, omit tier-unlock data and return only the count so the client can show the upgrade teaser.
- GET /trivia/stats: total answered, total correct, accuracy, current streak, best streak (streak = consecutive Eastern days answered correctly). Available to all users. Per-category correct counts are included for all users.

Patch endpoint (paid only):
- GET /trivia/patches (or fold into stats if cleaner): all 9 categories with current tier, correct count, next threshold, tier unlock dates, and totals, INCLUDING categories the user hasn't started. Free users get the same locked/403 response the existing Trophy Case endpoints return.

# 7. ACHIEVEMENT PATCH INTEGRATION

Roster already has an embroidery-style achievement patch system that is a paid feature. First inspect how it works (tables, progress tracking, unlock logic, display, paid gating) and extend it rather than building a parallel system. Reuse its existing progress and notification mechanisms.

## Category-to-patch mapping
- Each of the 9 trivia categories maps to exactly one patch family via trivia_category_patches.
- Create a placeholder patch family for each category if one doesn't exist (name, description, 8 tiers) with placeholder art I can replace later.

## Progress rules and tiers
- Each correct answer adds exactly 1 to that question's category count, for every user. No difficulty weighting. An incorrect answer adds nothing and never reduces the count.
- Tiers per category, determined by cumulative correct answers in that category:
  - Tier 1: 1 correct
  - Tier 2: 5 correct
  - Tier 3: 10 correct
  - Tier 4: 25 correct
  - Tier 5: 50 correct
  - Tier 6: 100 correct
  - Tier 7: 150 correct
  - Tier 8: 200 correct
- Store thresholds in config so I can change them without a deploy.
- Tier is derived from the correct count; one answer can unlock at most one tier. Store the unlock date for each tier the first time it's reached.
- Free users: counts and tier unlock dates are recorded silently in the background. Tiers are not displayed, celebrated, or pushed to them. When a free user upgrades, the Trophy Case shows their earned tiers right away. A tier earned while on the free plan should NOT trigger a retroactive flood of unlock celebrations on upgrade; show them as already unlocked (use the "new" indicator at most once, if it exists).
- Counts are cumulative and never expire. Tier 8 is the max; show a "Complete" state after that.
- Record the answer and increment the category count in the same database transaction so a retry or double tap can never double count. progress_awarded on trivia_answers is 0 or 1 so the test-mode reset can reverse it.
- Use "Tier 1" through "Tier 8" naming, or the existing patch system's tier naming if it has one.
- Fallback questions count the same way as generated ones.
