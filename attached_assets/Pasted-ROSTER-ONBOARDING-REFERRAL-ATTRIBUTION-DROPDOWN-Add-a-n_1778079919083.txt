ONBOARDING STEP UI
Add a new step (or insert into existing step) with the question:
"Who referred you to Roster?"
Display a single dropdown/select component with the following options, in this order:

Approved Partners — pulled dynamically from the referral_partners table where status = 'approved', sorted alphabetically by org_name. Display the org name only (not the referral code).
Other — when selected, reveals an optional text input field below the dropdown labeled "How did you hear about us?" (free text, max 200 characters)
None — default selection, no further action required

The dropdown should be optional but visible — users can select "None" and proceed.
Add a "Continue" button at the bottom that saves the selection and advances to the next onboarding step.

DATA HANDLING
Update the users table to ensure these columns exist (add if missing):

referral_partner_id (uuid, nullable, foreign key → referral_partners.id)
referral_source_other (text, nullable — stores the free-text input when "Other" is selected)

When the user submits the onboarding step:
If an approved Partner is selected:

Save referral_partner_id to the user's record in users table
Also save the partner's referral_code to the existing users.referral_code column for backward compatibility with the existing webhook handler
Call Purchases.setAttributes({ referral_code: "[CODE]", referral_partner_id: "[UUID]" }) on the RevenueCat SDK so the attribution is attached to the subscriber before any future purchase
Insert a tracking row into a new referral_user_links table (see schema below) — this captures ALL referred users, not just paid ones

If "Other" is selected:

Save the free-text response to users.referral_source_other
Leave referral_partner_id and referral_code null
No RevenueCat attribute needed

If "None" is selected:

No data saved to referral fields
Proceed normally


NEW SUPABASE TABLE — referral_user_links
This table tracks every user linked to a partner, regardless of paid status. This is separate from referral_conversions, which only tracks paying subscribers.

id (uuid, primary key)
referral_partner_id (uuid, foreign key → referral_partners.id)
user_id (text, not null — Roster user ID)
linked_at (timestamp, default now())
is_paid (boolean, default false — updated when the user becomes a paying subscriber)
paid_tier (text, nullable — 'player_pro' or 'commissioner', set when user converts)
paid_at (timestamp, nullable)

Create a unique constraint on (referral_partner_id, user_id) to prevent duplicates.

UPDATE REVENUECAT WEBHOOK HANDLER
Modify the existing /api/webhooks/revenuecat-referral endpoint:
When an INITIAL_PURCHASE event is received for a user with a referral code:

Insert into referral_conversions (existing behavior — keep this)
ALSO update the matching row in referral_user_links to set is_paid = true, paid_tier = the appropriate tier ('player_pro' or 'commissioner'), and paid_at = current timestamp
Use the user_id and referral_partner_id to find the matching row

When a CANCELLATION or REFUND event is received:

Update the referral_conversions row's status field as before
Update the matching referral_user_links row to set is_paid = false (the user is no longer paying)

Sorted alphabetically by org_name. Cache this endpoint for 5 minutes since it doesn't change often.

EDGE CASES TO HANDLE

If the approved partner list is empty, the dropdown should still show "Other" and "None" options
If the API call to fetch partners fails, gracefully fall back to showing only "Other" and "None" so onboarding doesn't break
If a user goes back and changes their selection during onboarding, properly clean up the previous selection (delete the old referral_user_links row, clear the old referral_code and referral_partner_id fields)
If a partner is later revoked (status changed from 'approved' to 'rejected'), do NOT delete historical referral_user_links rows — keep the data for accuracy
