Subject: Paywall presentation fix — RevenueCat is not the blocker; correct our identity read-back

Summary
The onboarding paywall failure was not a RevenueCat problem and not a login failure. Our own pre-paywall guard blocked presentation because it read the wrong identity field. RevenueCat does not gate paywall presentation in any way. Below is what the RevenueCat records show, what to change, and the exact behavior we want.

What the RevenueCat records confirm

The logIn(<custom id>) call succeeded. The custom-ID customer record now contains the device's anonymous ID ($RCAnonymousID:…) as an alias, along with its purchase history — this is a completed alias/merge, which only happens when logIn is received and processed by the backend. The ~216 ms success callback was accurate.
After an anonymous→custom merge, RevenueCat's documented behavior is that original_app_user_id becomes the anonymous ID and app_user_id becomes the provided custom ID. Reference: https://www.revenuecat.com/docs/customers/identifying-customers
Therefore, reading back an anonymous value is expected after a successful merge — it is not evidence that login failed.
Root cause
Our pre-paywall guard was checking customerInfo.originalAppUserId (or an equivalent "original" field). After a merge, that field is expected to be the anonymous ID, so the guard saw "anonymous," concluded login failed, and stopped before calling showPaywall. The guard was reading the wrong field, and it was gating the wrong action.

Change 1 — Do NOT gate paywall presentation on identity
RevenueCat renders the current offering to any account regardless of history or identity. Our offering is current, the paywall is published and attached, and all four products are live/approved. Presentation requires no identity check.

Remove the identity read-back condition in front of showPaywall.
Behavior we want: when onboarding reaches its final step, call showPaywall(true, undefined, callback). The trigger is 100% ours to decide — any account (new, anonymous, or with prior history) must see the paywall.
Change 2 — Move identity verification to purchase time, and read the correct field
We still care who the account is — but only at the moment of purchase, so a charge lands on the right account. This check must read the SDK's current app user ID, not the "original" one.

Authoritative read-back = the SDK's current appUserID (iOS: Purchases.shared.appUserID). This answers "who am I logged in as right now."
Do not use customerInfo.originalAppUserId for this — it is expected to be anonymous after a merge.
Pre-purchase assertion (pseudocode):
// At tap of Buy, BEFORE invoking the purchase:
const current = Purchases.appUserID;        // current identity
if (current !== expectedCustomAccountId) {
    abort purchase;
    re-run logIn(expectedCustomAccountId);
    re-read appUserID and confirm it matches;
}
// only then proceed with the purchase
Expose the current appUserID through the bridge so we can assert on it. If the bridge currently surfaces customerId from originalAppUserId, switch it to appUserID.
Change 3 — Prevent cross-account merges on shared/reused devices
Note for correctness (does not affect presentation): calling logIn(<new id>) while the SDK still holds a different cached identity will merge the prior identity's purchases into the new account. On our test iPad this actually happened — a previously cached anonymous production purchaser's history merged into the test account (no active entitlement leaked because it had already expired, but an active one would have transferred).

Before logIn(<custom id>), call logOut() first (or start from a fresh install) so a previously-cached user is not merged into the new account. This matters for purchase-time correctness, not for showing the paywall.
What we are NOT doing

Not changing anything in RevenueCat to "unblock" the paywall — there is nothing to change; it was never the blocker.
Not gating presentation on entitlements, history, or identity.
Acceptance criteria

On the final onboarding step, the paywall presents for any account (new, anonymous, or with history) with no identity precondition.
Purchases.shared.appUserID is exposed via the bridge and used for the pre-purchase assertion.
A purchase cannot proceed unless current appUserID equals the expected custom account ID.
logOut() precedes logIn() on identity switch (or fresh install) to prevent unintended merges.
